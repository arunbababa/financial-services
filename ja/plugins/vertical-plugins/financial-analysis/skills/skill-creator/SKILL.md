<a id="skill-creator"></a>
# スキルクリエイター

このスキルは、効果的なスキルを作成するためのガイダンスを提供します。

<a id="about-skills"></a>
## スキルについて

スキルはモジュール式の自己完結型パッケージであり、以下を提供することでClaudeの機能を拡張します。
専門的な知識、ワークフロー、ツール。特定の分野や課題向けの「オンボーディングガイド」と考えてください - Claudeを汎用エージェントから専門エージェントに変換します。
モデルが完全に持つことのできない手順の知識を備えています。

<a id="what-skills-provide"></a>
### スキルが提供するもの

1. 特殊なワークフロー - 特定のドメインに対する複数のステップの手順
2. ツールの統合 - 特定のファイル形式または API を操作するための手順
3. ドメインの専門知識 - 企業固有の知識、スキーマ、ビジネス ロジック
4. バンドルされたリソース - 複雑で反復的なタスク用のスクリプト、リファレンス、アセット

<a id="core-principles"></a>
## 基本原則

<a id="concise-is-key"></a>
### 簡潔さが鍵

コンテキスト ウィンドウは公共財です。スキルは、システム プロンプト、会話履歴、他のスキルのメタデータ、実際のユーザー リクエストなど、Claudeが必要とするものすべてとコンテキスト ウィンドウを共有します。

**デフォルトの仮定: Claudeはすでに非常に賢いです。** Claudeがまだ持っていないコンテキストのみを追加してください。それぞれの情報に挑戦してください:「Claudeは本当にこの説明が必要ですか?」 「この段落はトークンのコストを正当化しますか?」

冗長な説明よりも簡潔な例を好みます。

<a id="set-appropriate-degrees-of-freedom"></a>
### 適切な自由度を設定する

タスクの脆弱性と変動性に合わせて具体性のレベルを調整します。

**高い自由度 (テキストベースの指示)**: 複数のアプローチが有効な場合、決定がコンテキストに依存する場合、またはヒューリスティックがアプローチをガイドする場合に使用します。

**中程度の自由度 (疑似コードまたはパラメーターを含むスクリプト)**: 優先パターンが存在する場合、ある程度のバリエーションが許容される場合、または構成が動作に影響を与える場合に使用します。

**自由度が低い (特定のスクリプト、パラメータが少ない)**: 操作が脆弱でエラーが発生しやすい場合、一貫性が重要である場合、または特定のシーケンスに従う必要がある場合に使用します。

Claudeは道を探索していると考えてください。崖のある狭い橋には特定のガードレールが必要ですが (自由度が低い)、開けたフィールドでは多くのルートが可能です (自由度が高い)。

<a id="anatomy-of-a-skill"></a>
### スキルの構造

すべてのスキルは、必須の SKILL.md ファイルとオプションのバンドル リソースで構成されます。

```
skill-name/
├── SKILL.md (required)
│   ├── YAML frontmatter metadata (required)
│   │   ├── name: (required)
│   │   └── description: (required)
│   └── Markdown instructions (required)
└── Bundled Resources (optional)
    ├── scripts/          - Executable code (Python/Bash/etc.)
    ├── references/       - Documentation intended to be loaded into context as needed
    └── assets/           - Files used in output (templates, icons, fonts, etc.)
```

<a id="skillmd-required"></a>
#### SKILL.md (必須)

すべての SKILL.md は次のもので構成されます。

- **フロントマター** (YAML): `name` フィールドと `description` フィールドが含まれます。これらは、スキルがいつ使用されるかを判断するためにClaudeが読み取る唯一のフィールドであるため、スキルが何であるか、いつ使用する必要があるかを明確かつ包括的に説明することが非常に重要です。
- **本文** (Markdown): スキルを使用するための指示とガイダンス。スキルの発動後にのみ読み込みます（発動しても読み込まれない場合もあります）。

<a id="bundled-resources-optional"></a>
#### バンドルされたリソース (オプション)

<a id="scripts-scripts"></a>
##### スクリプト (`scripts/`)

決定論的な信頼性が必要なタスク、または繰り返し書き換えられるタスクの実行可能コード (Python/Bash など)。

- **どのような場合に含めるべきか**: 同じコードが繰り返し書き直される場合、または決定論的な信頼性が必要な場合
- **例**: PDF 回転タスクの場合は `scripts/rotate_pdf.py`
- **利点**: トークン効率が高く、挙動が決定論的であり、コンテキストにロードせずに実行できます。
- **注意**: パッチ適用や環境固有の調整のために、Claudeがスクリプトを読み取る必要がある場合があります。

<a id="references-references"></a>
##### 参考資料 (`references/`)

Claudeのプロセスと思考を知らせるために、必要に応じてコンテキストにロードされることを目的とした文書と参考資料。

- **含める場合**: Claudeが作業中に参照する必要があるドキュメント用
- **例**: 財務スキーマの場合は `references/finance.md`、会社の NDA テンプレートの場合は `references/mnda.md`、会社のポリシーの場合は `references/policies.md`、API 仕様の場合は `references/api_docs.md`
- **使用例**: データベース スキーマ、API ドキュメント、ドメイン知識、企業ポリシー、詳細なワークフロー ガイド
- **利点**: SKILL.md を無駄のない状態に保ち、Claudeが必要と判断した場合にのみロードされます。
- **ベスト プラクティス**: ファイルが大きい場合 (10,000語超)、SKILL.md に grep 検索パターンを含めます。
- **重複を避ける**: 情報は SKILL.md または参照ファイルの両方ではなく、どちらかに存在する必要があります。本当にスキルの中核となるものでない限り、詳細情報については参照ファイルを優先します。これにより、コンテキスト ウィンドウを占有することなく情報を検出できるようにしながら、SKILL.md を無駄のない状態に保ちます。 SKILL.md には、重要な手順とワークフローのガイダンスのみを保存します。詳細な参考資料、スキーマ、例を参考ファイルに移動します。

<a id="assets-assets"></a>
##### 資産 (`assets/`)

ファイルはコンテキストにロードされることを意図したものではなく、Claudeが生成する出力内で使用されます。

- **含めるタイミング**: スキルが最終出力で使用されるファイルを必要とする場合
- **例**: ブランド アセットの場合は `assets/logo.png`、PowerPoint テンプレートの場合は `assets/slides.pptx`、HTML/React ボイラープレートの場合は `assets/frontend-template/`、タイポグラフィの場合は `assets/font.ttf`
- **使用例**: コピーまたは変更されるテンプレート、画像、アイコン、定型コード、フォント、サンプル ドキュメント
- **利点**: 出力リソースをドキュメントから分離し、Claudeがファイルをコンテキストにロードせずに使用できるようにします。

<a id="what-to-not-include-in-a-skill"></a>
#### スキルに含めてはいけないもの

スキルには、その機能を直接サポートする必須ファイルのみを含める必要があります。次のような無関係なドキュメントや補助ファイルを作成しないでください。

- README.md
- INSTALLATION_GUIDE.md
- QUICK_REFERENCE.md
- CHANGELOG.md
- など

スキルには、AI エージェントが当面のジョブを実行するために必要な情報のみを含める必要があります。作成プロセス、セットアップとテストの手順、ユーザー向けドキュメントなどに関する補助的なコンテキストを含めるべきではありません。追加のドキュメント ファイルを作成すると、煩雑になり混乱が増すだけです。

<a id="progressive-disclosure-design-principle"></a>
### 漸進的な開示の設計原則

スキルは 3 レベルの読み込みシステムを使用してコンテキストを効率的に管理します。

1. **メタデータ (名前 + 説明)** - 常にコンテキスト内にあります (~100 単語)
2. **SKILL.md body** - スキルが発動したとき (<5,000 ワード)
3. **バンドルされたリソース** - Claudeの必要に応じて (コンテキスト ウィンドウを読み込まずにスクリプトを実行できるため無制限)

<a id="progressive-disclosure-patterns"></a>
#### 段階的な開示パターン

コンテキストの肥大化を最小限に抑えるために、SKILL.md の本文は必要不可欠な内容にまとめ、500 行未満に抑えます。この制限に近づくと、コンテンツを別のファイルに分割します。コンテンツを他のファイルに分割する場合は、SKILL.md からコンテンツを参照し、いつそれらを読み取るかを明確に記述して、スキルの読者がそれらの存在といつ使用するかを確実に認識できるようにすることが非常に重要です。

**重要な原則:** スキルが複数のバリエーション、フレームワーク、またはオプションをサポートしている場合は、コアのワークフローと選択ガイダンスのみを SKILL.md に保持します。バリアント固有の詳細 (パターン、例、構成) を別の参照ファイルに移動します。

**パターン 1: 参照資料へのリンクを持つ概要ガイド**

```markdown
# PDF Processing

## Quick start

Extract text with pdfplumber:
[code example]

## Advanced features

- **Form filling**: See [FORMS.md](FORMS.md) for complete guide
- **API reference**: See [REFERENCE.md](REFERENCE.md) for all methods
- **Examples**: See [EXAMPLES.md](EXAMPLES.md) for common patterns
```

Claudeは、必要な場合にのみ、FORMS.md、REFERENCE.md、または EXAMPLES.md をロードします。

**パターン 2: ドメイン特化型組織**

複数のドメインを持つスキルの場合は、無関係なコンテキストの読み込みを避けるためにコンテンツをドメインごとに整理します。

```
bigquery-skill/
├── SKILL.md (overview and navigation)
└── reference/
    ├── finance.md (revenue, billing metrics)
    ├── sales.md (opportunities, pipeline)
    ├── product.md (API usage, features)
    └── marketing.md (campaigns, attribution)
```

ユーザーが売上指標について質問すると、Claudeは sales.md のみを読み取ります。

同様に、複数のフレームワークまたはバリアントをサポートするスキルについては、バリアントごとに整理します。

```
cloud-deploy/
├── SKILL.md (workflow + provider selection)
└── references/
    ├── aws.md (AWS deployment patterns)
    ├── gcp.md (GCP deployment patterns)
    └── azure.md (Azure deployment patterns)
```

ユーザーが AWS を選択すると、Claudeは aws.md のみを読み取ります。

**パターン 3: 条件の詳細**

基本的なコンテンツを表示し、高度なコンテンツへのリンクを表示します。

```markdown
# DOCX Processing

## Creating documents

Use docx-js for new documents. See [DOCX-JS.md](DOCX-JS.md).

## Editing documents

For simple edits, modify the XML directly.

**For tracked changes**: See [REDLINING.md](REDLINING.md)
**For OOXML details**: See [OOXML.md](OOXML.md)
```

Claudeは、ユーザーがこれらの機能を必要とする場合にのみ、REDLINING.md または OOXML.md を読み取ります。

**重要なガイドライン:**

- **深くネストされた参照を避ける** - 参照は SKILL.md から 1 レベル深いものにします。すべての参照ファイルは SKILL.md から直接リンクする必要があります。
- **長い参照ファイルを構成する** - 100 行を超えるファイルの場合は、プレビュー時にClaudeが全範囲を確認できるように、先頭に目次を含めます。

<a id="skill-creation-process"></a>
## スキル作成プロセス

スキルの作成には次の手順が含まれます。

1. 具体例でスキルを理解する
2. 再利用可能なスキル コンテンツ (スクリプト、リファレンス、アセット) を計画する
3. スキルを初期化します (init_skill.py を実行)
4. スキルの編集（リソースの実装とSKILL.mdの書き込み）
5. スキルをパッケージ化します (package_skill.py を実行)
6. 実際の使用状況に基づいて反復する

以下の手順を順番に実行し、適用できない明確な理由がある場合にのみスキップしてください。

<a id="step-1-understanding-the-skill-with-concrete-examples"></a>
### ステップ 1: 具体例を使ってスキルを理解する

スキルの使用パターンがすでに明確に理解されている場合にのみ、このステップをスキップしてください。既存のスキルを使用する場合でも、それは依然として価値があります。

効果的なスキルを作成するには、スキルがどのように使用されるのか具体的な例を明確に理解します。この理解は、直接のユーザーの例、またはユーザーのフィードバックで検証された生成された例のいずれかから得られます。

たとえば、画像エディターのスキルを構築する場合、関連する質問には次のようなものがあります。

- 「画像エディターのスキルはどの機能をサポートする必要がありますか? 編集、回転、その他何か?」
- 「このスキルがどのように使用されるか例をいくつか挙げていただけますか?」
- 「ユーザーが『この画像から赤目を削除して』や『この画像を回転して』といったことを要求していると想像できます。このスキルが他に使用されると考えられる方法はありますか?」
- 「ユーザーはこのスキルをトリガーするために何と言うでしょうか?」

ユーザーに圧倒されないように、1 つのメッセージであまりにも多くの質問をしないようにしてください。最も重要な質問から始めて、効果を高めるために必要に応じてフォローアップしてください。

スキルがサポートすべき機能が明確になったら、このステップを終了します。

<a id="step-2-planning-the-reusable-skill-contents"></a>
### ステップ 2: 再利用可能なスキルのコンテンツを計画する

具体的な例を効果的なスキルに変えるには、次の方法で各例を分析します。

1. サンプルを一から実行する方法を検討する
2. これらのワークフローを繰り返し実行する場合に役立つスクリプト、参照、アセットを特定する

例: 「この PDF の回転を手伝ってください」のようなクエリを処理する `pdf-editor` スキルを構築する場合、分析では次のことがわかります。

1. PDF を回転するには、毎回同じコードを書き直す必要があります
2. `scripts/rotate_pdf.py` スクリプトをスキルに保存すると便利です

例: 「ToDo アプリを作成してください」または「歩数を追跡するダッシュボードを作成してください」などのクエリ用の `frontend-webapp-builder` スキルを設計する場合、分析では次のことがわかります。

1. フロントエンド Web アプリを作成するには、毎回同じボイラープレート HTML/React が必要です
2. ボイラープレート HTML/React プロジェクト ファイルを含む `assets/hello-world/` テンプレートは、スキルに保存すると役立ちます

例: 「今日ログインしたユーザーは何人ですか?」などのクエリを処理する `big-query` スキルを構築する場合。分析では次のことがわかります。

1. BigQuery にクエリを実行するには、毎回テーブルのスキーマと関係を再検出する必要があります
2. テーブルスキーマを文書化した`references/schema.md`ファイルは、スキルに保存すると役立ちます

スキルの内容を確立するには、各具体的な例を分析して、スクリプト、参照、アセットなどの再利用可能なリソースのリストを作成します。

<a id="step-3-initializing-the-skill"></a>
### ステップ 3: スキルの初期化

この時点で、実際にスキルを作成します。

開発中のスキルがすでに存在しており、反復またはパッケージ化が必要な場合にのみ、このステップをスキップしてください。この場合は、次のステップに進みます。

新しいスキルを最初から作成する場合は、必ず `init_skill.py` スクリプトを実行してください。このスクリプトは、スキルに必要なものすべてを自動的に含む新しいテンプレート スキル ディレクトリを便利に生成し、スキル作成プロセスをより効率的かつ信頼性の高いものにします。

使用法:

```bash
scripts/init_skill.py <skill-name> --path <output-directory>
```

スクリプト:

- 指定されたパスにスキルディレクトリを作成します
- 適切なフロントマターと TODO プレースホルダーを含む SKILL.md テンプレートを生成します
- リソース ディレクトリの例を作成します: `scripts/`、`references/`、および `assets/`
- カスタマイズまたは削除できるサンプル ファイルを各ディレクトリに追加します

初期化後、必要に応じて、生成された SKILL.md およびサンプル ファイルをカスタマイズまたは削除します。

<a id="step-4-edit-the-skill"></a>
### ステップ 4: スキルを編集する

(新規生成または既存の) スキルを編集するときは、Claudeの別のインスタンスが使用できるようにスキルが作成されていることに注意してください。Claudeにとって有益でありながら自明ではない情報も含めてください。別の Claude インスタンスがこれらのタスクをより効果的に実行するのにどのような手順知識、ドメイン固有の詳細、または再利用可能なアセットが役立つかを検討してください。

<a id="learn-proven-design-patterns"></a>
#### 実証済みの設計パターンを学ぶ

スキルのニーズに基づいて、次の役立つガイドを参照してください。

- **複数ステップのプロセス**: 順次ワークフローと条件付きロジックについては、references/workflows.md を参照してください。
- **特定の出力形式または品質基準**: テンプレートとサンプル パターンについては、references/output-patterns.md を参照してください。

これらのファイルには、効果的なスキル設計のための確立されたベスト プラクティスが含まれています。

<a id="start-with-reusable-skill-contents"></a>
#### 再利用可能なスキルコンテンツから始める

実装を開始するには、上記で特定した再利用可能なリソース (`scripts/`、`references/`、および `assets/` ファイル) から始めます。このステップではユーザー入力が必要になる場合があることに注意してください。たとえば、`brand-guidelines` スキルを実装する場合、ユーザーは `assets/` に保存するブランド アセットまたはテンプレート、または `references/` に保存するドキュメントを提供する必要がある場合があります。

追加したスクリプトは実際に実行してテストし、バグがないこと、および出力が期待どおりであることを確認する必要があります。類似したスクリプトが多数ある場合は、完了までの時間のバランスをとりながら、すべてが機能することを確信するために、代表的なサンプルだけをテストしても構いません。

スキルに必要のないサンプル ファイルとディレクトリは削除する必要があります。初期化スクリプトは、構造を示すために `scripts/`、`references/`、および `assets/` にサンプル ファイルを作成しますが、ほとんどのスキルではそれらすべてが必要というわけではありません。

<a id="update-skillmd"></a>
#### SKILL.mdを更新する

**書き方のガイドライン:** 常に命令形/不定詞形を使用してください。

<a id="frontmatter"></a>
##### フロントマター

`name` および `description` を使用して YAML フロントマターを書き込みます。

- `name`: スキル名
- `description`: これはスキルの主要なトリガー メカニズムであり、Claudeがスキルをいつ使用するかを理解するのに役立ちます。
  - スキルの機能と、それを使用する特定のトリガー/コンテキストの両方を含めます。
  - すべての「いつ使用するか」の情報をここに含めます - 本文には含めません。本体はトリガー後にのみロードされるため、本体内の「このスキルをいつ使用するか」セクションはClaudeにとって役に立ちません。
  - `docx` スキルの説明例: 「変更の追跡、コメント、書式設定の保存、テキスト抽出をサポートする包括的なドキュメントの作成、編集、分析。Claudeが次の目的で専門的なドキュメント (.docx ファイル) を操作する必要がある場合に使用します。(1) 新しいドキュメントの作成、(2) コンテンツの変更または編集、(3) 追跡された変更の操作、(4) コメントの追加、またはその他のドキュメント タスク。」

YAML フロントマターには他のフィールドを含めないでください。

<a id="body"></a>
##### 本体

スキルとそのバンドルされたリソースの使用手順を記述します。

<a id="step-5-packaging-a-skill"></a>
### ステップ 5: スキルをパッケージ化する

スキルの開発が完了したら、ユーザーと共有される配布可能な .skill ファイルにパッケージ化する必要があります。パッケージ化プロセスでは、最初にスキルが自動的に検証され、すべての要件を満たしていることが確認されます。

```bash
scripts/package_skill.py <path/to/skill-folder>
```

オプションの出力ディレクトリ指定:

```bash
scripts/package_skill.py <path/to/skill-folder> ./dist
```

パッケージ化スクリプトは次のことを行います。

1. **スキルを自動的に検証**し、以下をチェックします:

   - YAML フロントマター形式と必須フィールド
   - スキルの命名規則とディレクトリ構造
   - 説明の完全性と品質
   - ファイル構成とリソース参照

2. 検証に合格した場合はスキルを**パッケージ**し、スキルにちなんで名付けられた .skill ファイル (例: `my-skill.skill`) を作成します。このファイルにはすべてのファイルが含まれ、配布用に適切なディレクトリ構造が維持されます。 .skill ファイルは、.skill 拡張子が付いた zip ファイルです。

検証が失敗した場合、スクリプトはエラーを報告し、パッケージを作成せずに終了します。検証エラーを修正し、パッケージ化コマンドを再度実行します。

<a id="step-6-iterate"></a>
### ステップ 6: 反復する

スキルをテストした後、ユーザーは改善を要求する場合があります。多くの場合、これはスキルを使用した直後に、スキルがどのように実行されたかという新たなコンテキストとともに発生します。

**反復ワークフロー:**

1. 実際のタスクでスキルを使用する
2. 困難や非効率性に気づく
3. SKILL.md またはバンドルされたリソースを更新する方法を特定する
4. 変更を実装して再度テストする
